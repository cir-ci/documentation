A CI job sees a failure in two places: the exit code of `circi upload`, and the one-line `error:` message it prints. Both come from the CLI, which relays what the CI API answered. For the endpoints themselves, see the [CI API reference](/reference/ci-api/).

## Exit codes

| Command | Code | Meaning |
|---|---|---|
| `circi upload` | `0` | The upload succeeded. With `--wait`: the build passed, or the git host's check is the merge gate and the job doesn't fail on changes. |
| | `1` | With `--wait`: visual changes need review and this job is the gate. Approve them in the dashboard, then re-run the job. |
| | `2` | An error. Bad flags or setup, the server couldn't be reached, the build failed to process or had screenshots it couldn't read in a project that blocks merges, or `--wait` timed out. |
| `circi site upload`, `circi storybook upload` | `0` / `2` | Done, or an error (printed as one line). |

An error before the upload finishes (code `2`) comes with a line `error: <message>`. An error that is a bug rather than a mistake of yours also prints `(Run again with --debug, or set DEBUG=1, for the stack trace.)`; with `--debug` the stack follows the message.

A build that failed to process or that holds unreadable screenshots exits `2` only when the project blocks merges. In a project that doesn't, the job exits `0` and prints a `warning:` line. The server's reason is printed either way. See [How a build flows](/introduction/how-a-build-flows/#couldnt-read).

With `--wait`, a build whose result is `pending` is polled until it isn't, first every 0.5 seconds and then every 2 seconds at most, until `--timeout` (default 600 seconds). If the server can't be reached while waiting, the CLI prints `warning: <reason>; still waiting` once and keeps polling until the timeout.

## CLI messages

What `circi upload` prints, by the stage it was at: before uploading anything, while talking to the server, while waiting for the result, and when it reads the git history.

### Before the upload

<RefItem>

No `CIRCI_TOKEN` in the environment. Add the project's token as a CI secret.
</RefItem>
<RefItem>
<Fragment slot="term">`Set CIRCI_API_URL (or --api-url) to your CirCI address`</Fragment>

Neither the variable nor the flag is set.
</RefItem>
<RefItem>
<Fragment slot="term">`--timeout must be a positive number of seconds`</Fragment>

The value isn't a number above zero.
</RefItem>
<RefItem>
<Fragment slot="term">`--gate must be "status" or "exit-code"`</Fragment>

Any other value.
</RefItem>
<RefItem>
<Fragment slot="term">`--shard must look like 1/4` or `--shard must look like 1/4: this job's number, then how many jobs there are`</Fragment>

The shard isn't `n/total`, or `n` is outside `1` to `total`.
</RefItem>
<RefItem>
<Fragment slot="term">`Could not tell which CI run these shards belong to. Set CIRCI_PARALLEL_NONCE (or --nonce) to the same value in every shard.`</Fragment>

A sharded upload on a CI the CLI doesn't recognize.
</RefItem>
<RefItem>
<Fragment slot="term">`Could not determine the commit. Run inside a git checkout or set CIRCI_COMMIT.`</Fragment>

Not in a git checkout and no `CIRCI_COMMIT`.

<RefItem>

The folder argument is wrong.
</RefItem>
<RefItem>
<Fragment slot="term">`No .png files found in <dir>`</Fragment>

The folder holds no PNG, or only hidden folders and `node_modules`.
</RefItem>
<RefItem>

A screenshot over 25 MB.
</RefItem>
<RefItem>
<Fragment slot="term">`<path>.json isn't valid JSON (…)`, `<path>.json must contain a JSON object`</Fragment>

The metadata file next to a screenshot is broken.

<RefItem>

`circi site upload` refuses links and special files; the first five are named.

The CLI needs `git`.

The operating system's file descriptor limit.
</RefItem>
<RefItem>

A file problem on the CI machine, named by path.
</RefItem>

### Reaching the server

<RefList>
<RefItem>
<Fragment slot="term">`Couldn't reach https://ci.acme.io (connection refused)` followed by `Check CIRCI_API_URL.`</Fragment>

The server isn't reachable. The detail can be `host not found`, `connection reset`, `timed out`, `certificate expired`, `self-signed certificate` or `not a valid URL`. Check the address, the proxy and the certificate.
</RefItem>
<RefItem>
<Fragment slot="term">`The server refused the token (…). Check that CIRCI_TOKEN is this project's CI token.`</Fragment>

The server answered `401` or `403`. The token is wrong, belongs to another project, or was rotated or deleted with the project. The text in parentheses is the server's own.
</RefItem>
<RefItem>
<Fragment slot="term">`The server failed: … (HTTP 502)`</Fragment>

A `5xx` answer after the retries. See the server log.
</RefItem>
<RefItem>
<Fragment slot="term">`Upload of 3fa9c1d20b4e failed: 413 …`</Fragment>

One file couldn't be sent; the first 12 characters of its hash say which. The server's reason follows.
</RefItem>
<RefItem>
<Fragment slot="term">`Server asked for unknown file <sha256>`</Fragment>

The server asked for a file the CLI didn't offer. Report it.
</RefItem>
<RefItem>
<Fragment slot="term">`<n> files didn't arrive; sending again`</Fragment>

Not an error: finalizing reported missing files and the CLI sent them again once. If finalizing then fails again, the message is the server's.
</RefItem>
</RefList>

Every API call is retried up to 4 times in all, with waits of about 0.5, 1 and 2 seconds (each scaled by a random 50 to 100 percent), after a network failure, a `429` or any `5xx` answer. A request times out after 30 seconds, and a file or site upload after 2 minutes. `400`, `401`, `403`, `404`, `409`, `413`, `415` and `422` aren't retried: they won't change. Every call the CLI makes is safe to repeat.

### Waiting for the result

<RefList>
<RefItem>
<Fragment slot="term">`error: timed out waiting for the build to be processed`</Fragment>

`--timeout` ran out. Exit `2`. The build keeps processing; look at it in the dashboard, or raise `--timeout`.
</RefItem>
<RefItem>
<Fragment slot="term">`error: Build #12 failed to process: <reason>`</Fragment>

The pipeline failed. The line after it is `Details: <build url>`.
</RefItem>
<RefItem>
<Fragment slot="term">`error: <screenshot name>: <reason>` and `Upload the build again with valid PNGs: <url>`</Fragment>

A screenshot couldn't be read, for example because it isn't a valid PNG. One line per screenshot.
</RefItem>
<RefItem>
<Fragment slot="term">`Review the changes at <url>` and `After approving, re-run this job to unblock the merge: <job url>`</Fragment>

Exit `1`. The job is the gate.
</RefItem>
<RefItem>
<Fragment slot="term">`warning: <text>` after the summary</Fragment>

The build passes, but something needs a look; for example merges aren't blocked for this project.
</RefItem>
</RefList>

The summary line reads `<outcome>: N changed, N added, N removed, N unchanged`, with `, N couldn't be read` when some are unreadable. The outcomes are listed in the [CI API reference](/reference/ci-api/#get-v1buildsidstatus).

### Git history warnings

The CLI collects the history CirCI uses to choose a baseline. When it can't, it prints `warning: <reason>. CirCI will compare against the latest <default branch> build instead.` and the upload carries on.

<RefList>
<RefItem>
<Fragment slot="term">`Not inside a git repository`</Fragment>

Run in a checkout.
</RefItem>
<RefItem>
<Fragment slot="term">`Commit <sha> is not available locally`</Fragment>

The checkout lacks the head commit.
</RefItem>
<RefItem>
<Fragment slot="term">`Could not read the commit history (shallow clone)`</Fragment>

Deepen the checkout.
</RefItem>
<RefItem>
<Fragment slot="term">`Base branch "<name>" is not available from origin`</Fragment>

Fetch the base branch, or check `CIRCI_BASE_BRANCH`.
</RefItem>
<RefItem>
<Fragment slot="term">`No common history with "<name>" within 2000 commits; use a deeper checkout (e.g. fetch-depth: 0)`</Fragment>

Use a full clone, or a deeper one.
</RefItem>
</RefList>

## Errors from the CI API

The reply is `{ "error": "…" }`, with `fields` on validation failures; see [Conventions](/reference/ci-api/#conventions).

<RefList>
<RefItem labelName="HTTP status" label="400">
<Fragment slot="term">The request is invalid.</Fragment>

Messages are plain sentences about a field ("Commit sha isn't in the right format", "Branch must be 255 characters or fewer"), or one of: `Invalid build name "<name>": use letters, digits, ".", "_" or "-" (max 64)`, `Invalid commit SHA "<sha>"`, `ancestorShas must be at most 2000 commit SHAs`, `parallel.total must be between 1 and 1000`, `Invalid screenshot name "<name>"`, `Duplicate screenshot name "<name>"`, `The archive contains no files`, `A <kind> needs <entry page> at its top level` (for example `A Storybook needs index.html at its top level`), or a message about an unsafe site archive. Fix the request.
</RefItem>
<RefItem labelName="HTTP status" label="401">
<Fragment slot="term">`A valid project token is required (Authorization: Bearer circi_…)`.</Fragment>

Send the project's CI token.
</RefItem>
<RefItem labelName="HTTP status" label="403">
<Fragment slot="term">`Static site hosting is off for this project: turn it on in the project settings`.</Fragment>

Turn **Host static sites** on.
</RefItem>
<RefItem labelName="HTTP status" label="404">
<Fragment slot="term">`Build not found`; `This file wasn't requested by any build (POST /v1/builds first)`; `Static site hosting isn't set up on this server`.</Fragment>

The build isn't in this project; create the build first; set `STATIC_SITES_HOST`.
</RefItem>
<RefItem labelName="HTTP status" label="409">
<Fragment slot="term">`N file(s) weren't uploaded or failed verification` with `missing`; `Build #N is already <status>; it can't take more screenshots`; `Another shard of this build already uploaded a screenshot with one of these names`.</Fragment>

Send the missing files and finalize again; upload a new build; use unique names across shards.
</RefItem>
<RefItem labelName="HTTP status" label="413">
<Fragment slot="term">`Files are limited to 26214400 bytes`, or a hosted site over a limit (see [Limits](/reference/limits/)), or a JSON body over 16 MB.</Fragment>

Shrink the file, or split the build.
</RefItem>
<RefItem labelName="HTTP status" label="415">
<Fragment slot="term">`Send the file as image/png or application/octet-stream`; `Send the site as application/gzip (a .tar.gz)`.</Fragment>

Fix the `content-type`.
</RefItem>
<RefItem labelName="HTTP status" label="422">
<Fragment slot="term">`The uploaded bytes hash to <hash>, not <hash>`.</Fragment>

The file changed or was damaged in transit; send it again.
</RefItem>
<RefItem labelName="HTTP status" label="500">
<Fragment slot="term">`Internal server error`.</Fragment>

See the server log.
</RefItem>
</RefList>

<Aside type="note">
A request that fails in the dashboard's own JSON API (`/api`) uses the same `{ "error": "…" }` shape, with `400` for invalid input, `403` for a forbidden action and `404` for something that doesn't exist or that you can't see. Errors from an integration's provider map to `400`, `404`, `409` or `502` when the provider is unreachable.
</Aside>
