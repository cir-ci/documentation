CirCI is a pnpm and Turborepo monorepo. Code is split into five layers, and the dependencies between them are checked by a test (`packages/services/test/layers.test.ts`) and by lint overrides in `.oxlintrc.json`, so a wrong import fails before review.

## The layers

Read the diagram from the top: a request enters at the transport layer and each layer calls the one below it. `core` and `api` depend on nothing.

| Layer | Lives in | May import |
| --- | --- | --- |
| Transport | `apps/server` (`http/`, `cli/`, `composition/`), `apps/worker`, `apps/web` | Services, `@circi/db/queries` (read models) and types. Never repositories, the queue, the schema, `drizzle-orm` or `pg`. The composition root is the one app folder that wires the database |
| Services | `packages/services/src/<area>/` | Core, db, adapters. No app, Fastify, auth, api or config |
| Core | `packages/core` | Nothing from `@circi`, no I/O. `@circi/core` is browser-safe; `@circi/core/node` holds the Node-only secrets, tokens and signing |
| Db | `packages/db` | Core. Never services, integrations, storage, auth or api |
| Adapters | `packages/integrations`, `storage`, `diff`, `sites` | At most core (`integrations` also `api`), never db, services or Fastify |

`packages/config` and `packages/api` (wire types, types only) sit beside the stack: `config` imports at most `core`, and nothing outside config reads `process.env`. `packages/auth` imports no service or app, and the web app imports no server package.

## Folders

```text
apps/server      the circi command: HTTP routes (CI API, dashboard, sign-in), admin CLI, composition
apps/worker      background jobs: claim loop and thin job adapters (inlined in the server bundle)
apps/web         the dashboard (React, TanStack Router and Query, Base UI), organized by feature
packages/api     the wire types of the dashboard API (types only)
packages/auth    better-auth composition, admin operations
packages/cli     circi upload for CI
packages/config  environment parsing and validation
packages/core    rules with no I/O: baselines, pairing, outcomes, limits, slugs, review rules
packages/db      Drizzle schema, migrations, repositories, queries (dashboard read models), queue
packages/diff    PNG validation, pixel diffs (JS, worker threads, native Rust), thumbnails
packages/integrations  the integration SDK and one folder per kind (GitHub, GitLab, ...)
packages/services      use cases: transactions, repositories, queued jobs and notices
packages/sites         hosted-site handling
packages/storage       local-disk and S3 drivers, checksum-verified writes
packages/testing       db-free test support
packages/ui            the design system: Base UI parts, CSS modules, --circi-* tokens
packages/vitest        @circi/vitest
deploy/ dev/ e2e/ perf/ docs/
```

## The rules

- **`@circi/db` subpaths say the layer.** Import `@circi/db/queries`, `/repositories`, `/queue` or `/schema`; the root is the connection, errors and shared types.
- **Repositories store and look up, nothing else.** They never queue jobs; a repository that changes something returns what happened and the caller decides what follows.
- **Services own every change that triggers something.** The service opens the transaction and queues the jobs and notices, so a webhook delivery or check run exists exactly when the change is committed (a transactional outbox). The build pipeline is the one exception: it is idempotent step by step, so no connection is held across image work.
- **Read models** (`db/queries`) are shaped for the dashboard, and their return types must fit `@circi/api`: `apps/server/src/contract-check.ts` fails to typecheck if they drift. Routes may call them directly.
- **Routes decide no roles.** Use the policies in `services/src/access`. A route file stays under 250 lines.
- **Better-auth's tables** (`schema/auth.ts`) are generated (`pnpm db:auth-schema`, then `pnpm db:generate`), never edited by hand.
- **Fastify scopes** receive exactly their dependencies; register a scope with a prefix through a wrapper plugin, so the plugin's options never carry `prefix`.

A file that breaks a rule on purpose is a named exception in the test, with its reason.

## Where does new code go?

| You are adding | Put it in |
| --- | --- |
| An endpoint | The route in `apps/server/src/http/routes/<area>/`, the use case in `packages/services/src/<area>/`, the read model in `packages/db/src/queries/`, the store in `packages/db/src/repositories/`, the wire type in `packages/api` |
| A background job | A body in `services/src/jobs/` or the area folder and a thin adapter in `apps/worker/src/handlers/`. Never a new job name or payload key without a rolling-deploy plan, because queued rows outlive a deploy |
| A pure rule | `packages/core` |
| An integration | One folder under `packages/integrations/src/kinds/`, listed once in the registry (see [Integrations overview](/integrations/overview/)) |

Services tests mirror the folders under `packages/services/test/`.

## Conventions

- Types that belong to something live in type-only namespaces (`createBuild.Input`, `Row.Props`, `Build.Detail`). A namespace contains only types, never a value.
- Imports use the `#folder/*` aliases from each package's `package.json`, not `../../..` climbs.
- CSS modules: `styles.root`. Colors and sizes come from `--circi-*` tokens, never copied hex values.
- Copy: contractions with the straight apostrophe, "ID", "Delete" for something gone for good and "Remove" for taking it out of a list, "screenshot" never "snapshot".
