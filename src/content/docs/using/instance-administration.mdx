An **instance** is one CirCI installation. **Instance admins** run it: they manage every account and workspace, the server's settings and its health. This is separate from the workspace roles in [Members and roles](/using/members-and-roles/): an instance admin isn't automatically a member of any workspace, and sees a workspace's projects only if they belong to it.

## Where to open it

Instance admins have **Instance admin** in the account menu and an **Instance** entry in the sidebar. The hub lists three groups:

| Group | Page | What it holds |
|---|---|---|
| People | Accounts | Everyone who can sign in, and who runs the instance |
| Workspaces | All workspaces | Every workspace, new and deleted ones |
| Server | Instance settings, Health | Address, sign-in methods, mail, who can create workspaces; checks and background jobs |

The first account created during first-run setup becomes the first instance admin. See [Sign in and set up](/getting-started/sign-in-and-set-up/).

## Accounts

A searchable, paged list (up to a page of accounts at a time). **Create account** takes a **Name**, an **Email**, how they first sign in (**Show a generated password** or **Email a sign-in code**), an optional password, and **Make them an instance admin**. A generated password is shown once, in a dialog: pass it on yourself, because CirCI doesn't keep it readable.

Each account's actions menu offers:

- **Change email**: takes effect at once with no confirmation mail, so it works without mail and for a lost mailbox. They stay signed in.
- **Reset password**: signs them out everywhere and shows a new password once.
- **Make instance admin** or **Remove instance admin**. The last instance admin can't be removed.
- **Sign out everywhere**.
- **Ban** (with an optional reason and number of days; empty means no end) or **Lift ban**. Banning signs the person out at once; their reviews stay in each build's history.

The same actions exist in `circi admin user` on the server. See [Admin CLI](/reference/admin-cli/).

## Workspaces

Every workspace with its size, each opening its settings hub. **New workspace** asks for a **Name** and the **Owner's email**, which must already have an account; the owner invites the rest. Deleted workspaces are in a group of their own with the days left. A workspace's owner deletes it, it is purged after 30 days, and an instance admin can **Restore** it or **Delete permanently** from its hub. See [Workspace settings](/using/workspace-settings/).

Otherwise what you save applies within about 30 seconds on every server process, with no restart, and secrets are write-only and sealed at rest. Most of the page waits for **Save changes**, with **Discard** to revert. The single sign-on providers and the GitHub App apply from their own dialogs.

| Section | What you set | Variable that locks it |
|---|---|---|
| Dashboard address | Read-only: the address every outgoing link uses, and old addresses that redirect to it | `PUBLIC_URL`, `PREVIOUS_PUBLIC_URLS` |
| Sign-in methods allowed | Password, email code and single sign-on: the outer limit, which each workspace can only narrow. Saving refuses a change that leaves nobody able to sign in | `AUTH_PASSWORD_ENABLED`, `AUTH_EMAIL_ENABLED`, `AUTH_SSO_ENABLED` |
| Single sign-on providers | GitHub, Google, GitLab and OpenID Connect providers for every workspace, added, changed and removed in a dialog. Providers set by `AUTH_*` variables are listed read-only | `AUTH_*` |
| Who can create workspaces | Instance admins only, or every signed-in account | `WORKSPACE_CREATION` |
| Mail server | The SMTP server and sender, and **Send a test mail to your own address** | `SMTP_HOST` and the other `SMTP_*` |
| Slack app | The client ID and secret of the instance's Slack app | `SLACK_CLIENT_ID`, `SLACK_CLIENT_SECRET` |
| Storage and limits | The storage driver (read-only), then the retention new projects start with (30 days, no variable), the grace period for unused files, the upload timeout, job retention and webhook timeout | `STORAGE_DRIVER`, `GC_GRACE_HOURS`, `UPLOAD_TIMEOUT_MINUTES`, `JOB_RETENTION_DAYS`, `WEBHOOK_TIMEOUT_SECONDS` |
| Hosted sites | The sites domain (read-only) or "Not set up", and the largest site | `STATIC_SITES_HOST`, `STATIC_SITES_MAX_MB` |

Without mail, nobody gets sign-in codes or invitations by email. See [Configuration](/self-hosting/configuration/) and [Environment variables](/reference/environment-variables/).

### GitHub App

One click on **Create GitHub App** sends you to GitHub with the App's name, address, permissions and events filled in. You confirm it there and install it on your account or organization. Checks and pull request comments are all it asks for. CirCI stores what GitHub returns, encrypted, on this instance. The **App name** must be unique across GitHub, and the organization field can stay empty to use your account. The badge says whether the App is **Not set up**, from the **Environment** (`GITHUB_APP_*`, edited there) or **Created here**. See [GitHub](/integrations/github/).

### Address changes

When the dashboard's address changes, instance admins see a banner and a **Moving to …** checklist on Health: old links redirect, but a few registrations outside CirCI (such as the GitHub App's webhook) still name the old address. The checklist can be dismissed and shown again.

## Health

**Run checks again** reruns the same findings as `circi admin doctor`, grouped as **Services**, **Domains and cookies** (best effort: it can only check hosts it knows) and a summary of Passing, Need a look and Failing. It also shows **Background jobs** (waiting, running, oldest waiting, retrying, failed) per queue, and the **Setup code** state: only needed on a fresh install, where the code is in the server log or from `circi admin setup-code`. See [Scaling the worker](/self-hosting/scaling-the-worker/).
