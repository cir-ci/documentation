A build is one upload of screenshots from CI. When it has changes against the baseline, someone looks at each changed screenshot and approves or rejects it. The build's status follows from those decisions. This page covers the build screen; [Comments and regions](/using/comments-and-regions/) covers the discussion beside it.

Anyone who can see the project can approve, reject, comment and ask for reviews: project members, and owners and admins of the workspace. See [Members and roles](/using/members-and-roles/).

## Open a build

Open a project and choose a build from its list, follow the link in a pull request comment or check, or open a review request from [Reviews or the Inbox](/using/inbox-and-reviews/). The page title is the build number (and its name, when it isn't `default`), with the branch under it.

The header shows the build's state:

| State | Meaning |
|---|---|
| Uploading, Processing | CI is still sending files, or the server is comparing. The page updates by itself when processing is done. |
| Needs review | The build finished with changes nobody has decided yet. |
| Approved, Rejected | The decisions on its changed screenshots add up to that. |
| No changes | Nothing differs from the baseline. |
| No baseline | There was nothing to compare with. The first build of a project is like this: every screenshot is new, and later builds are compared with it once it is approved. |
| Failed | The build errored. The message is shown under the header. |
| Expired | Its screenshots were deleted under the project's retention. See [Project settings](/using/project-settings/). |

Next to the state the header can show the review target (for example "22h left" or "Overdue 2h"), and how many people are watching the build: its author and whoever was asked to review.

## The screenshot list

The list on the left groups the screenshots in review order. A group is only shown when it has screenshots.

| Group | Starts | Contents |
|---|---|---|
| Changed | open | Same name as a baseline screenshot, but different pixels (above the project's diff threshold) |
| Added | open | A screenshot with no baseline |
| Removed | open | A baseline screenshot the build didn't upload |
| Flaky | collapsed | Changed screenshots known to be flaky on the default branch. See [Triage and flaky screenshots](/using/triage-and-flaky-screenshots/) |
| Failed | open | Screenshots that couldn't be compared |
| Unchanged | collapsed | Identical or within the threshold |

Each row shows a status icon, the name, the number of comment threads, and a short figure: the percentage of pixels that changed, or "resized" when the dimensions differ. Above the list, "2 of 5 reviewed" counts the screenshots that need a decision and have one. Press `j` and `k` to move through the list; a collapsed group counts as one stop, opened with Enter.

Right-click a row for Open, Open in new tab, Copy link, Copy name, Approve, Reject and View baseline. Approve and Reject only appear when the decision isn't already in force.

## Look at a change

The viewer has four compare modes, chosen with the View control or the keys 1 to 4:

| Key | Mode | Shows |
|---|---|---|
| `1` | Side by side | Baseline and new screenshot next to each other |
| `2` | Overlay | The new screenshot with the changed pixels in red on top; the Diff layer slider sets how strong |
| `3` | Diff | Only the changed pixels |
| `4` | Slider | A divider you drag between baseline and new screenshot |

Zoom is Fit or 100%, with buttons to step in and out, and View options has a Checkerboard background for transparent screenshots. Previous and next buttons walk the list. Click an image to enlarge it.

<Aside type="note">
Key `5` is reserved for a Design view of the Figma frame a screenshot comes from. The build screen doesn't offer it yet.
</Aside>

## Decide

Decisions are made per screenshot. Each acts at once and shows a toast with **Undo**.

- **Approve** (`a`) approves the screenshot on screen and moves on to the next one that still needs a decision.
- **Reject** (`r`) asks for a reason first. The screenshot is marked rejected, which holds back the merge, and it never becomes a baseline. The reason goes to the build's author in their Inbox and to the pull request. A project can make the reason optional; see [Project settings](/using/project-settings/).
- **Approve all** (`Shift` + `a`) approves every changed screenshot that has no decision yet. It is the page's one primary button.

Cmd + Enter sends the reason from its text field. Approve and Reject only appear on a finished build with changes. A decision can be changed later: the latest one counts.

### What the decisions add up to

The build's review status is derived from its screenshots: all changed screenshots approved means the build is **Approved**; one rejected means **Rejected**; anything else is still **Needs review**. Unchanged screenshots need no decision. When the status moves, the author is notified, webhooks fire (see [Webhooks](/integrations/webhooks/)), and the check on the pull request is updated. People who were asked to review stop being asked once the build is decided.

On the project's default branch, an approved screenshot becomes the baseline later builds are compared with. A default-branch screenshot can be accepted as a baseline even while the rest of the build is still pending. Other branches only count once the whole build is approved. See [Baselines and ignore regions](/using/baselines-and-ignore-regions/).

### Merge gate

With a repository linked, the pull request check follows the build. By default unreviewed changes keep it pending until someone approves; rejected changes fail it. Whether it blocks merging depends on the project's merge gate settings, and whether the repository marks the check as required. See [Project settings](/using/project-settings/) and [GitHub](/integrations/github/).

## The sidebar

Three tabs sit beside the viewer.

- **Details**: the pull request, commit, branch, when it was uploaded, and the baseline it was compared with and how it was chosen ("where this branch started", or the latest build on the default branch when git history wasn't available). Below that: who was asked to review, how the selected screenshot changed over recent default-branch builds, linked issues, and every decision made so far with its reason.
- **Activity**: what happened to the build, oldest first: upload, checks, review requests, decisions, comments and issues created.
- **Comments**: see [Comments and regions](/using/comments-and-regions/).

When the baseline is a fallback, a warning banner says which build was used. Fetch more git history in CI (for example `fetch-depth: 0` on GitHub Actions) for an exact comparison. See [CI examples](/ci/ci-examples/).

## Ask for a review

**Request review** opens a list of the project's members (never yourself). Choosing someone creates an open request, which shows up in their Reviews and Inbox. Asking someone who is already asked does nothing. See [Review requests and rules](/using/review-requests-and-rules/).

If the project has Linear or Jira mapped, **Create issue** also appears in the header and files an issue for the selected screenshot. See [Linear](/integrations/linear/) and [Jira](/integrations/jira/).

## Approve many builds at once

On a project's builds list, press `x` to select builds (or select rows with the checkboxes). A bar at the bottom offers **Approve**, **Reject** (with a reason), **Request review** and **Clear selection**. This works inside one project; a workspace-wide list only browses. The list has filters, grouping and ordering; see [Saved views](/using/saved-views/).

## Keyboard shortcuts

| Key | Does |
|---|---|
| `j` / `k` | Next or previous screenshot |
| `a` | Approve the screenshot |
| `Shift` + `a` | Approve all |
| `r` | Reject, with a reason |
| `c` | Write a comment |
| `1` to `4` | Compare mode |
| `Cmd` + `Enter` | Send a comment or confirm the dialog you are typing in |
| `?` | Show every shortcut |

Plain keys are switched off while you are typing in a comment field. On a phone the list and the discussion open as sheets from a bar at the bottom, and Approve all, Request review and Copy link sit in its More sheet.
