CirCI needs one Postgres database. Postgres holds all of its data except the files, which live in [storage](/self-hosting/storage/). The compose file runs `postgres:18-alpine` with its data in the `pgdata` volume (Postgres 18 images keep data under `/var/lib/postgresql/<major>/`, so mount the volume at `/var/lib/postgresql`). A managed Postgres works as well.

## Connect

<SettingCard name="DATABASE_URL" required type="URL">
Where Postgres is, for example `postgres://circi:password@db.internal:5432/circi`. The server and the worker both read it.
</SettingCard>

<SettingCard name="DATABASE_POOL_MAX" defaultValue="10" type="number">
The most connections one process keeps open. A server and a worker each take up to this many, so a managed database needs room for the sum across every process you run.
</SettingCard>

### Connection rules

<Aside type="caution" title="Use a direct connection or session pooling">
The worker wakes on Postgres `LISTEN/NOTIFY`, which a transaction pooler (PgBouncer in transaction mode) doesn't support. Without a live notification connection the worker polls every second instead, so builds start a little later but still run. Point `DATABASE_URL` at Postgres directly, or use session pooling.
</Aside>

If a connection drops, the process reconnects by itself.

The job queue lives in the same database as the data, so a webhook delivery or a check run is queued in the same step as the change that caused it: both happen or neither does.

## Migrations

SQL migrations live in `packages/db/migrations` (`/app/migrations` in the image). `circi serve`, `circi worker` and `circi all` apply pending migrations on start unless you pass `--no-migrate`.

<Steps>

1. **Back up first.** See [Backups](/self-hosting/backups/).

2. **Pull the new image and restart.** The first process to start applies the migrations.

3. **Migrate separately.** To apply migrations without serving:

   ```sh
   docker compose exec circi circi migrate
   ```

</Steps>

See [Upgrades and migrations](/self-hosting/upgrades-and-migrations/) for the order to follow when you run several processes.

## Health

`circi admin doctor` reports whether the database is reachable and how many migrations are applied. **Instance** › **Health** shows the same under Services, and the queue depth under Background jobs. `GET /readyz` fails when the database can't be reached.
