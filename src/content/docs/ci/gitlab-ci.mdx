This guide takes a GitLab project from nothing to a visual status on every merge request: a CirCI project and token, a pipeline that takes screenshots and uploads them, a commit status that blocks the merge until someone reviews the changes, and sharding for a slow suite. [CI examples](/ci/ci-examples/) has the short versions for every CI system. For GitHub, see the [GitHub Actions guide](/ci/github-actions/).

You need a running CirCI server ([Run it locally](/getting-started/run-it-locally/) or [Self-hosting](/self-hosting/requirements/)) that your runners can reach, and tests that write PNG screenshots to a folder. The examples use Playwright writing to `./screenshots` ([how to set that up](/ci/playwright/)); [Cypress](/ci/cypress/), [Storybook](/ci/storybook/) and the [Vitest plugin](/ci/vitest/) have their own pages, and the pipeline changes only in the lines that take the screenshots.

## 1. Create the project and store its token

<Steps>

1. In CirCI, create a project for the thing you test and copy its CI token, which is shown once ([Create a project](/getting-started/create-a-project/)).

2. In GitLab, open the project's **Settings** › **CI/CD** › **Variables** and add `CIRCI_TOKEN` with the token, and `CIRCI_API_URL` with your CirCI address (for example `https://ci.acme.io`).

</Steps>

<Aside type="caution" title="Protected variables">
A variable marked **Protected** is passed only to pipelines on protected branches and tags, so a merge request from an ordinary branch wouldn't see it and the upload would stop with `Set CIRCI_TOKEN to the project CI token`. Leave it unprotected unless every branch you test is protected.
</Aside>

The token can only upload builds and read the status of its own project's builds. If it leaks, rotate it in the project's settings and update the variable; the old one stops working at once.

## 2. Write the pipeline

The CLI reads the commit, branch, merge request number and target branch from the variables GitLab sets, so the pipeline passes none of them. It reads the merge request's number and target only in a **merge request pipeline**, because GitLab sets `CI_MERGE_REQUEST_IID` and the other `CI_MERGE_REQUEST_*` variables nowhere else. In a branch pipeline CirCI sees the commit and the branch and no merge request. So run the job for merge requests and for the default branch, whose builds are the baselines. In `.gitlab-ci.yml`:

```yaml title=".gitlab-ci.yml"
visual:
  image: mcr.microsoft.com/playwright:v1.65.1-noble
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  variables:
    GIT_DEPTH: "0"
  script:
    - npm ci
    - npx playwright test
    - npx @circi/cli upload ./screenshots --wait
```

Why each part is there:

- **Both rules.** A merge request is compared with the nearest earlier approved build of the same project and build name, found from the merge request's merge base. The builds of the default branch are those baselines, so the default branch must upload too. With **Approve default-branch builds automatically** on, which is the default, a build of the default branch moves the baseline without another review ([How a build flows](/introduction/how-a-build-flows/#which-baseline)).
- **`GIT_DEPTH: "0"`.** GitLab clones shallowly by default, and the CLI needs history to find the baseline. A shallow checkout works, because the CLI fetches the base branch and a little more, but a full fetch is faster on large repositories ([CLI reference](/ci/cli/#git-history)).
- **The Playwright image.** It has the browsers, Node and git, and its tag must match the `@playwright/test` version in your `package.json`. Screenshots differ between operating systems and font sets, so take them in the same image every time. [Make screenshots stable](/ci/playwright/#make-screenshots-stable) lists what else moves a pixel.
- **`--wait`.** Without it the job ends when the upload does. With it the job waits for the result and prints it: how many screenshots changed, were added or removed, and where to review them.

<Aside type="note" title="What was run, and what wasn't">
The pipeline wasn't run on GitLab. What was run: the published `@circi/cli` 0.2.0, given the variables GitLab sets in a merge request pipeline, reported the merge request's source commit, its branch, the merge request number and the target branch `main`; given the variables of a branch pipeline, it reported the commit and branch and no merge request. The commit status in step 3 is described from [the GitLab integration](/integrations/gitlab/), which has been tested only against simulated services and not against gitlab.com or a self-managed GitLab.
</Aside>

## 3. Get a status on each merge request

Without a linked repository, the job itself is the gate: `--wait` exits `1` while changes need review, and the pipeline fails. To get a `CirCI / default` commit status on the merge request, a summary note and `/circi` commands instead:

<Steps>

1. In GitLab, create an access token with the `api` scope. In CirCI, open **Workspace settings** › **Integrations** › **Add integration** › **GitLab**, enter your GitLab address and the token, and connect.

2. Add the webhook on GitLab: **Settings** › **Webhooks**, with the URL `PUBLIC_URL/webhooks/gitlab`, the secret token the integration's page shows, and merge request and comment events as triggers.

3. On the integration's page, choose the GitLab project the CirCI project reports to.

4. In the GitLab project's merge request settings, require the status to pass so that it blocks the merge.

</Steps>

Each step has its details in [the GitLab integration](/integrations/gitlab/#set-up). The status is named `CirCI / <build name>`, and the build name is `default` until you pass `--name`. It fails while changes wait for review (when **Unreviewed changes block merging** is on, which is the default) and turns to success once someone approves in the dashboard or with a `/circi approve` note. GitLab statuses have no Approve and Reject buttons.

If the instance has no GitHub App configured, the server can't tell that a GitLab-linked project reports to a git host, so pass `--gate status` to make GitLab's status the gate and not the job: `npx @circi/cli upload ./screenshots --gate status --wait`. Who blocks the merge, the status or the job, is explained in [How a build flows](/introduction/how-a-build-flows/#merge-gate).

## 4. Shard a slow suite

Run the tests in parallel jobs and give each its share. Every job uploads its own screenshots, and CirCI joins them into one build and processes it when the last shard arrives:

```yaml title=".gitlab-ci.yml"
visual:
  image: mcr.microsoft.com/playwright:v1.65.1-noble
  parallel: 4
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  variables:
    GIT_DEPTH: "0"
  script:
    - npm ci
    - npx playwright test --shard=$CI_NODE_INDEX/$CI_NODE_TOTAL
    - npx @circi/cli upload ./screenshots --shard $CI_NODE_INDEX/$CI_NODE_TOTAL --wait
```

The shards find each other through the pipeline's ID. A shard that never arrives fails the build after `UPLOAD_TIMEOUT_MINUTES` (default 60), naming the missing shards.

## When something goes wrong

| What you see | What to do |
|---|---|
| `Set CIRCI_TOKEN to the project CI token` | The variable isn't set, or it is protected and the branch isn't. |
| `Couldn't reach https://ci.acme.io` | The runner can't reach your server: check the address, the firewall and the certificate. |
| `The server refused the token` | The token belongs to another project, or was rotated. |
| No merge request on the build | The job ran in a branch pipeline. Add the `merge_request_event` rule. |
| The status never appears | The project isn't linked to this GitLab project, or the webhook isn't added ([GitLab troubleshooting](/integrations/gitlab/#troubleshooting)). |
| Every screenshot is "added" on a merge request | The project has no approved baseline yet. Approve the first build, on the default branch, once. |
| The job exits `1` | A project that isn't linked uses the job as the gate. Approve the changes in the dashboard, then retry the job. |

Every message the CLI prints is in [Errors and exit codes](/reference/errors-and-exit-codes/).
