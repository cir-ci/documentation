The GitLab integration works with gitlab.com and self-managed GitLab. Each build of a linked Project shows on the merge request as a commit status named `CirCI / <build name>`, and CirCI keeps one summary note on the merge request up to date. People can approve, reject or rerun with `/circi` commands in a note.

It differs from [GitHub](/integrations/github/) in three ways: it uses an access token instead of an App, GitLab statuses have no Approve and Reject buttons, and you add the webhook on GitLab yourself.

## Connect GitLab

An owner or admin of the Workspace does this under **Workspace settings**, **Integrations**, **Add integration**, **GitLab**.

<Steps>

1. In GitLab, create an access token with the `api` scope. A project, group or personal access token works; use one whose account can see the repositories you want to report to and can post statuses and notes.
2. In CirCI, enter the **GitLab address** (`https://gitlab.com` or your self-managed address) and the **Access token** (`glpat-…`).
3. Connect. CirCI asks GitLab who the token belongs to and lists the projects it can read, so a wrong address, a rejected token or a token without the `api` scope fails here with a message.

</Steps>

A connection is identified by the token's user on that GitLab server (`host#user`), so the same GitLab user can't be connected in two Workspaces. Connecting again with a new token replaces the credentials and clears a "needs attention" flag. If GitLab later rejects the token, the integration shows the reason and asks for a new one.

A self-managed address must be public unless the instance sets `WEBHOOK_ALLOW_PRIVATE_ADDRESSES` (see [Environment variables](/reference/environment-variables/)).

## Add the webhook on GitLab

CirCI can only learn about merge requests and notes if GitLab calls it. On the GitLab integration's page, owners and admins see the address and the secret to use. In each GitLab project (or group) open **Settings**, **Webhooks** and add:

- **URL**: `PUBLIC_URL/webhooks/gitlab` (the alias `PUBLIC_URL/api/integrations/gitlab/webhook` also works).
- **Secret token**: the secret shown on the integration's page. It's derived from the instance secret, so it doesn't change unless the instance secret does.
- **Trigger events**: merge request events and comments.

GitLab sends the secret in the `X-Gitlab-Token` header. CirCI refuses deliveries without it.

## Link a Project to a GitLab project

On the integration's page, choose the **GitLab project** each CirCI Project reports to, written as the path with its namespace, for example `acme/web` or `acme/team/web`. The list comes from the repositories the token can read; you can also type the path. A Project reports to one git host at a time.

## What shows on the merge request

- **Commit status.** One per build name, `CirCI / <build name>`. It's `running` while screenshots are processed, `success` when there are no changes, the changes are approved, or the Project doesn't block merging, and `failed` when changes await review with merge blocking on, or when they are rejected. The description is the same title the GitHub check uses, such as "3 changed: review required", and it links to the build.
- **Summary note.** One note per merge request, edited in place, with a table of builds (status, changes, review state) and any hosted sites for the newest commit.

Statuses have no buttons, so review happens in the dashboard or with commands. To block merging, require the status to pass in the GitLab project's merge request settings. The **Merge gate** settings on the CirCI Project page apply as they do for GitHub.

## Commands

In a note on the merge request, put one of these on a line of its own:

| Command | What it does |
| --- | --- |
| `/circi approve` | Approves the newest build of each build name on the merge request |
| `/circi reject` | Rejects them |
| `/circi rerun` | Processes them again |

CirCI answers with a thumbs-up reaction on the note when it acted, and with a thumbs-down plus a short reply when it didn't. Edits of a note don't repeat the action.

A person may use commands when they have linked their GitLab login to their CirCI account and can see the Project (a member, or an owner or admin of its Workspace). CirCI matches the GitLab user ID, never the email. Others get a reply explaining how to link.

<InstanceSettingNote setting="GitLab sign-in">
Linking a GitLab login needs GitLab sign-in to be configured on the instance. Set it in Instance settings, or by `AUTH_GITLAB_CLIENT_ID` and `AUTH_GITLAB_CLIENT_SECRET` as the initial value, plus `AUTH_GITLAB_URL` for a self-managed GitLab (default gitlab.com). See [Instance settings](/self-hosting/instance-settings/).

## What the webhook handles

- Merge request opened or reopened: remembers the author and gives builds their merge request number. Other merge request updates aren't used.
- Note created on a merge request: the `/circi` commands.

## The merge gate in CI

`circi upload --wait` decides who blocks the merge: the status on GitLab, or the CI job (see [the CLI](/ci/cli/)). The server picks the status as the gate when a Project reports to a git host, but today it only knows that when the GitHub App is configured on the instance. On an instance without a GitHub App, a GitLab-linked Project defaults to the CI job being the gate (exit code 1 until approved). To make GitLab's status the gate there, pass `--gate status`.

## Not built

- Approve and Reject buttons on the status (GitLab has none).
- GitLab-specific events beyond merge request open, reopen and notes: for example, nothing happens when a merge request is closed (GitHub closes its review requests).
- Reporting a Project to more than one GitLab project.
