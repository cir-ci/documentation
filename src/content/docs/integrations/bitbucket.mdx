The Bitbucket integration supports Bitbucket Cloud. Each build of a linked project shows on the pull request as a commit status named `CirCI / <build name>`, and CirCI keeps one summary comment on the pull request up to date. It's the smallest of the three git integrations: statuses and comments, with commands, but no buttons.

| You get | Where |
| --- | --- |
| A commit status per build name | The pull request's builds section |
| One summary comment per pull request | The pull request's activity |
| `/circi approve`, `/circi reject`, `/circi rerun` | A comment on the pull request |
| One help comment, which also holds each command's answer | The same activity, edited in place |

## Set up

An owner or admin of the workspace opens **Workspace settings**, **Integrations**, **Add integration**, **Bitbucket**.

<Steps>

1. In Bitbucket, create a workspace or repository access token that can read and write pull requests. An app password also works.
2. In CirCI, enter the **Bitbucket workspace** ID (`acme` in `bitbucket.org/acme`; lower case letters, digits, dashes and underscores) and the **Access token**. For an app password, also enter the **Username** it belongs to.
3. Connect. CirCI lists the workspace's repositories with the token, so a rejected token, a token that can't read the workspace, or an unknown workspace fails here with a message.
4. Add the webhook on Bitbucket (below).
5. On the integration's page, choose the repository each CirCI Project reports to, written `workspace/repository` (for example `acme/web`).
6. To block merging, add a merge check in Bitbucket that requires the build status to pass.

</Steps>

A connection is one Bitbucket workspace, and that workspace can be connected in one CirCI Workspace only. Connecting again with a new token replaces the credentials and clears a "needs attention" flag.

### Add the webhook on Bitbucket

On the Bitbucket integration's page, owners and admins see the webhook address and the secret. In each Bitbucket repository open **Repository settings**, **Webhooks** and add:

- **URL**: `PUBLIC_URL/webhooks/bitbucket` (the alias `PUBLIC_URL/api/integrations/bitbucket/webhook` also works).
- **Secret**: the secret shown on the integration's page. It's derived from the instance secret.
- **Triggers**: pull request created, updated, and comment created.

CirCI checks the `X-Hub-Signature` header on every delivery.

## What appears where

### The commit status

One per build name. The key is `circi-` plus a short hash of the build name, so each build name keeps its own status, and it links to the build. The description is the same title the GitHub check uses.

| Situation | Status |
| --- | --- |
| Processing | `INPROGRESS` |
| No changes, approved, or the project doesn't block merging | `SUCCESSFUL` |
| Changes await review and merging is blocked, or rejected | `FAILED` |
| Some screenshots couldn't be read (`1 screenshot couldn't be read`) | `FAILED` when the project blocks merging, `SUCCESSFUL` otherwise, until the build is uploaded again |

### The summary comment

One comment per pull request, edited in place, with the same text as the [GitHub summary comment](/integrations/github/#the-summary-comment): a table of builds and any hosted sites for the newest commit. A build with screenshots that couldn't be read says "1 screenshot couldn't be read" in its review cell.

### Commands

Comment `/circi approve`, `/circi reject` or `/circi rerun` on a line of its own. Bitbucket has no reactions, so CirCI always answers in its **one help comment per pull request**, edited in place with the latest answer:

- When it acted: "Done: approved the latest CirCI build" (or "rejected", or "rerunning the latest CirCI builds").
- When it didn't: the reason from the [GitHub page](/integrations/github/#commands-in-comments): no build yet, still processing, processing failed, or nothing to decide.
- When it can't match you to an account: "I couldn't tell who you are in CirCI. Link your Bitbucket account to a CirCI account that belongs to this project's workspace (`PUBLIC_URL`), then try again."

<Aside type="caution">
CirCI has no Bitbucket sign-in provider (the sign-in providers are GitHub, GitLab, Google and OpenID Connect), so there is currently no way for a person to link a Bitbucket account to their CirCI account in the dashboard. Until that exists, `/circi` commands on Bitbucket get the "couldn't tell who you are" answer. Review in the dashboard instead. A person could use commands once CirCI can match their Bitbucket account ID to a CirCI account in the project's workspace.
</Aside>

## Settings

The **Merge gate** settings on the CirCI Project page apply as they do for GitHub: **Unreviewed changes block merging**, **Flaky-only changes block merging** and **Approve default-branch builds automatically**. A build with screenshots that couldn't be read follows **Unreviewed changes block merging** too: it fails when that is on and passes, with the count in the description, when it is off.

### The merge gate in CI

`circi upload --wait` decides who blocks the merge: the status on Bitbucket or the CI job (see [the CLI](/ci/cli/)). The server picks the status as the gate when a project reports to a git host, but today it only knows that when the GitHub App is configured on the instance. On an instance without it, a Bitbucket-linked project defaults to the CI job being the gate (exit code 1 until approved). Pass `--gate status` to make Bitbucket's status the gate.

## Troubleshooting

| What you see | Why, and what to do |
| --- | --- |
| Connect fails with a message | The token was rejected, can't read the workspace, or the workspace ID is wrong. For an app password, check the **Username** too |
| Statuses appear but no comment | The webhook isn't added, or its secret doesn't match. Check the webhook's request log in Bitbucket |
| Every command gets the "couldn't tell who you are" answer | Expected today: see the caution above. Review in the dashboard |
| The integration shows **needs attention** | Bitbucket rejected the token. Connect again with a new token |

## What the webhook handles

- Pull request created or updated: remembers the author, and gives builds their pull request number by matching the source commit or branch.
- Comment created on a pull request: the `/circi` commands.

Nothing happens when a pull request is merged or declined.

## Not built

- Approve and Reject buttons (Bitbucket statuses have none).
- Bitbucket Server and Data Center. Only Bitbucket Cloud is supported.
- Linking a Bitbucket account for commands, as described above.
